# Telegram Rich Messages: правила агента

Общение, интерфейс и документация — на русском. Python 3.11+, только стандартная библиотека. Текущий репозиторий — готовый личный сервис: пользователь поручает агенту подготовку/правки, смотрит превью и разрешает публикацию в Telegram. Голосовой ввод предоставляет агентная среда; дашборд — просмотр и история.

## Начало нового чата

1. Прочитай README.md, ONBOARDING.md и короткий HANDOFF.md. Проверь cwd и `git status --short --branch`, сохрани чужие изменения.
2. Следуй текущему запросу: запуск и первая настройка — это онбординг, а не продолжение разработки. Не читай планы/архивы без конкретной необходимости и не начинай с них ответ. Не перечисляй отсутствующие функции и исследовательские ограничения по своей инициативе; на прямой вопрос отвечай честно по коду.
3. Определи фактические ОС, shell, папку и Python. Пользователю давай только подходящую ветку: Windows → PowerShell/`py -3`; macOS → Terminal/`python3`. Не объявляй сервис предназначенным только для ОС текущего агента или старого тестового хоста. Для remote/контейнера/WSL отделяй среду агента от компьютера человека.
4. Веди по одному ручному шагу. Пользователь не должен знать JSON, CLI, ID и Rich Markdown. Технические действия выполняет агент.

## Пример и рабочая история

Демо необязательно. Предложи временный пример или сразу собственный пост. Для примера используй `preview-demo --port PORT`: он работает в отдельной временной папке, не читает токен и не добавляет посты в личную историю. После просмотра останови процесс демонстрации; рабочий сервис запускай из фактической папки командой `serve`.

Не используй постоянные `demo`/`demo-media` в рабочем корне при онбординге. Не удаляй существующие примеры, посты, SQLite или receipts автоматически. Старые установки могут содержать пользовательские правки в примерах.

## Telegram

Перед привязкой обязательно прочитай [docs/TELEGRAM-SETUP.md](docs/TELEGRAM-SETUP.md) и следуй выбранной ветке по одному ручному шагу. Основной реальный случай — существующий канал; бот может уже быть администратором, но токен всё равно нужно явно сохранить в этой установке. Не путай эти факты. Пользователь присылает целую ссылку канала/поста; check --chat разбирает её сам. Для приватного канала без постов есть отдельная ветка, не проси ссылку на несуществующий пост.

Не открывай за человека якобы ожидающий token-set в служебном терминале. Объясни открытие нового собственного Terminal/PowerShell, дай реальные cd/Set-Location и token-set, покажи строку скрытого ввода и ожидаемый JSON «сохранён в защищённом хранилище». Попроси прислать только итог команды или скриншот нижней части терминала после завершения. Не проси токен. Даже если бот существующий и человек знает BotFather, эту инструкцию сохранения не пропускай. /token не предлагать как безобидный просмотр: он генерирует новый токен; по умолчанию нужен действующий.

Независимо предложи существующий/новый канал и существующего/нового бота. Создавай только по выбранной ветке. Не требуй замены существующего бота. Для обычного постинга нужен бот-администратор канала с правом публикации. Обсуждения, личные сообщения каналу, цена и второй пользовательский аккаунт не нужны.

Токен вводит только человек через `token-set` со скрытым вводом. Не проси его в чате, не читай из хранилища и не выводи. Не читай `secrets/`, `*.env`, `*.pem`; не печатай credential-bearing URL. Секрет получает только локальный процесс при явно запрошенном действии. macOS: Keychain через stdin; Windows: DPAPI/ACL. Linux/WSL-хранилище доставки не поддержано; plaintext fallback запрещён.

Показывай одну подходящую инструкцию терминала с реальной папкой. macOS: Cmd+Space → Терминал, `cd`, `python3 tool.py token-set`, Cmd+V, Enter. Windows: Пуск → PowerShell без администратора, `Set-Location -LiteralPath`, `py -3 tool.py token-set`, Ctrl+V, Enter. Объясни скрытый ввод; ExecutionPolicy не менять.

Не удаляй сообщения/ботов, не меняй webhook и не отзывай токен общего бота. Не читай его updates. `discover --isolated-bot-consent` — только для выделенного бота после явного согласия на одно чтение, при активном webhook команда останавливается. ID/username назначения сверяй, не угадывай по названию.

## Сохранение материала

Канонические блоки: heading, paragraph, list, image, video, media_group, quote, details, table, button. Группа — image/video leaves, layout collage/slideshow. Никакого произвольного HTML и обхода compiler. Unicode сохраняется без нормализации; custom_emoji требует точного числового ID и fallback, не угадывай ID по символу.

`Store(root)` хранит неизменяемые версии в SQLite, экспортирует posts/POST_ID/vNNNN.json/.md/.html. `create/import` создают материал, `update` добавляет версию. Чтобы изменить текст и сохранить медиа, передай полный набор `--blocks`: `--text/--file` заменяет прежние блоки. `update --media` без нового текста добавляет файлы. `--root PATH` передаётся до подкоманды.

Готовый `--text/--file` разбивается по пустым строкам на абзацы. Строки с явными `- ` и последовательными `1. `, `2. ` становятся списками; авторское длинное тире `—` остаётся текстом с переносом. Для цитат, заголовков, вложений и точного порядка используй `--blocks`. Перед разрешением доставки сверяй итоговый `snapshot.markdown` с блоками и превью: человеку показывай читаемую структуру абзацев, списков и переносов, без требования разбирать Markdown.

Медиа копируются в media/, оригиналы не меняются. Путь/MIME/SHA256/размеры и duration видео перепроверяются перед сохранением и доставкой; symlink и выход за media запрещены. PNG без interlace и baseline JPEG до 10 MiB; nonfragmented MP4 H.264/AVC с необязательным AAC до 50 MiB. Неподдерживаемые форматы явно отклоняются, скрытой конвертации нет.

## Разрешение доставки

Подготовка/настройка и имеющиеся доступы не разрешают отправку. `review POST_ID --action send|edit` выполняет сетевую проверку и связывает версию, назначение, бота, media и прежнее сообщение. Покажи конкретный текст/превью, версию/хеш, порядок/хеши медиа, бота, канал/тему и действие. Для edit покажи изменения и тот же message_id.

Только после явного разрешения этих данных — `execute OPERATION_ID --fingerprint VALUE`. Fingerprint не заменяет согласие. Изменения версии, бота, назначения, прав или предыдущей публикации требуют нового review и разрешения. Сознательная повторная публикация требует отдельного разрешения и `--new-publication`.

Не повторяй unknown. Сначала offline recover, устойчивый receipt сохраняется до SQLite/HTML. Известный message_id запрещает повтор из-за ошибки HTML. Resolve — только по проверенным человеком фактам с evidence; known receipt нельзя объявить отсутствующим. Не обходи блокировку активной операции новым ID или прямым Python API. Исторические сетевые адаптеры вне текущего сценария не включать.

API success не доказывает вид. `verify-visual POST_ID --confirmed` только после подтверждения человеком текущей опубликованной версии; playback учитывается отдельно.

## Проверки, UI и перенос

`python3 -m unittest discover -s tests -q`; `node --check web/app.js`. Выбирай проверки по изменению. После UI-правок проверяй доступным браузером desktop/mobile, детали, фильтры, клавиатуру и media. Если browser policy запрещает URL, не обходи запрет и не объявляй визуальный проход выполненным.

Сохраняй Onest, JetBrains Mono, нейтральную палитру и плотность из DESIGN.md и .impeccable/design.json. Исторический внешний визуальный источник не нужен для первого запуска и не меняется.

Сохраняй чужие изменения. Пользовательские posts/media/data/index, secrets и config.local.json исключены из Git. Переносить posts/media/data вместе при остановленных операциях; токен на новом компьютере человек вводит заново. Commit/push, публикации, удаление данных и изменение доступов требуют актуального поручения в своём объёме.

Технические детали для изменения кода и разбора старых операций: [docs/development/agent-reference.md](docs/development/agent-reference.md). При обычной настройке этот архив не нужен.

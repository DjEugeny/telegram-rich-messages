# Спецификация: серверное расписание Rich Messages

## 1. Результат и предел доказательства — R01, R02, R18

Пользователь поручает агенту подготовить версию и дату. Локальный инструмент сохраняет проверенный план; experimental-адаптер передаёт Rich Message в direct messages канала и вызывает approveSuggestedPost с датой. Никакого исполнителя в момент выхода нет. Запрещены локальный таймер, heartbeat Codex, cron, внешний постоянно работающий сервис, обычные сообщения вместо Rich Message, пользовательская MTProto-сессия и авторизация аккаунта.

Официальная документация подтверждает параметры, но НЕ доказывает самоодобрение предложения ботом-администратором: роли отправителя и одобряющего требуют live проверки. Реализация обозначается экспериментальной, пока не пройдена §8. Если API отклонит сценарий, код сохраняет точный этап/результат, фиксирует препятствие и не заявляет готовность; другой способ возможен только по явному согласованию с пользователем и лишь такой, который сохраняет серверный выход без локального исполнителя, без подмены цели локальным таймером/cron/обычным сообщением.

SuggestedPostParameters: now+300 … now+2678400 секунд. Документация называет верхний предел «30 days», хотя число равно 31 суткам: используем число секунд, прямо объясняем расхождение. Запрещены цена, paid broadcast и любые платежи.

## 2. Настройки и время — R03, R04, R07, R16

Как новичок, я называю канал и зону, чтобы агент выполнил технические шаги. Приёмка: сохраняются явные channel_id/@username, dm_chat_id, direct_messages_topic_id, IANA timezone. Настройка не выдаёт разрешение сети. Токен остаётся в прежнем системном хранилище, token-set запускает человек.

Как пользователь, я говорю «завтра в 18:00», чтобы получить точное время. Приёмка: локальный разбор возвращает абсолютный ISO 8601, Unix timestamp и зону. Поддерживаем ISO дата+время и однозначные «сегодня/завтра/послезавтра в ЧЧ:ММ»; дни недели, отсутствие часов/зоны, прошлое, DST gap/fold отклоняются до сети. Агент может интерпретировать более сложную фразу, но обязан показать итог; неоднозначность требует уточнения при реальном поручении, никакой молчаливой догадки.

Ошибочная или отсутствующая зона даёт понятную ошибку. Стандартная библиотека zoneinfo при отсутствии системной базы IANA объясняет препятствие, не устанавливает пакет и не подменяет зону UTC. Даты повторно проверяются перед каждым сетевым действием.

## 3. Snapshot и разрешение — R05, R06, R14, R22

Как пользователь, я разрешаю конкретный вариант, канал, бота и дату. Приёмка: review сохраняет version/hash, markdown/media из compiler, bot ID, подтверждённый канал и DM-parent, topic, дату/зону, исходные настройки и publication anchor. Fingerprint включает всё это и ID операции. Review проверяет can_post_messages и can_manage_direct_messages, DM is_direct_messages/parent_chat. Произвольная тема не считается проверенной: API send может отказать.

Изменение версии, media, бота, назначения, даты, зоны либо прежней публикации делает прежний review недействительным. Проверки актуальности повторяются под SQLite write lock после preflight; агент показывает человеку понятный результат review перед сетевым действием. Старые versions/exports/media не меняются, не удаляются и не пересоздаются. Новые таблицы создаются без перестройки старых данных.

Как пользователь, я редактирую локальный черновик, не меняя принятую Telegram версию. Приёмка: snapshot остаётся прежним, UI показывает номер запланированной версии и отличие от текущей.

## 4. Доставка и устойчивость — R08, R09, R19, R20

Как пользователь, я получаю «Запланирован» только после одобрения Telegram. Приёмка: execute с experimental opt-in и fingerprint делает sendRichMessage в dm_chat_id/topic с suggested_post_parameters.send_date, проверяет возвращённые chat/message/suggested_post_info; fsync proposal receipt предшествует approveSuggestedPost. Только строго True одобрения и устойчивый receipt дают scheduled. Proposal ID не считается будущим channel message_id.

Состояния: reviewed (локальная проверка), sending, proposed (предложение принято, расписание не подтверждено), approving, scheduled, unknown, error, cancelled, published. При отказе approve остаётся известное proposed с ошибкой; повторное создание блокируется. При timeout/невалидном ответе sending/approving → unknown; повтор execute и новая отправка того же поста заблокированы. Receipt каждого шага пишется атомарно с fsync до SQLite-проекции и HTML; отказ записи сохраняет доступное подтверждение в SQLite и оставляет recovery без повторной сети.

Одна OS delivery.lock общая с непосредственной доставкой. Оба пути проверяют активные операции другого. Конкурентный execute не создаёт второе предложение. Rebuild failure не отменяет успех Telegram. Повтор completed execute возвращает receipt без сети. Если процесс умер между шагами, recover использует известные receipts и никогда не продолжает сеть сам.

## 5. Восстановление, перенос, отмена — R10, R12, R13, R21

Как пользователь, я возвращаюсь после срока. Приёмка: recover без сети восстанавливает receipts; время само не превращает scheduled в published. Список/дашборд пишут «Время наступило; публикация не подтверждена».

Bot API не документирует надёжный перенос/отмену approved suggested post. Редактирование approved/declined запрещено; decline не обещает отмену approved; deleteMessage не обещает снять расписание. Команды reschedule/cancel обязаны дать понятный unsupported без сети и без ложного успеха. Не выполнять deleteMessage или «новое предложение + удаление старого». Это удовлетворяет требованию проверить поддержку, но полноценный перенос/отмена остаются неподтверждёнными до нового доказанного механизма.

Как пользователь, я сообщаю проверенный факт Telegram, чтобы восстановить состояние. Приёмка: отдельная локальная reconcile требует непустое evidence и точный schedule ID; published требует channel message_id и назначение исходного snapshot. cancelled допускается только по подтверждённой человеком фактической отмене, без отправки API. Факт не считается API подтверждением. Известный успешный receipt не разрешается объявить отсутствующим. Повторное подтверждение идемпотентно, конфликтующий ID/переход отклоняется. Нельзя отменой локальной записи снимать неизвестную сеть без явного свидетельства.

Ни getUpdates, ни смены webhook, ни чтения хранилища агентом. Updates/канал не опрашиваются автоматически. Надёжной автоматической связи proposal→channel publication Bot API не обещает; ручное свидетельство сохраняет источник. Exactly-once не заявляется.

## 6. Просмотр — R11, R15

Как пользователь, я вижу очередь, дату с зоной, канал, версию, ошибку и источник подтверждения. Приёмка: CLI schedule-list без токена; в дашборде фильтры новых статусов, дата и зона именно расписания, заметное experimental/live-unverified, состояния pending/proposed/unknown не называются scheduled. После срока — отдельный текст, версия snapshot не смешивается с текущей. Пустой список понятен. Onest, нейтральные токены, клавиатура и отсутствие overflow сохраняются. UI не получает кнопок доставки и API записи.

## 7. Инструкции — R16, R17, R28

Голос распознаёт агентная среда. ONBOARDING содержит протокол поручений: подготовить/показать/изменить/запланировать/показать очередь/перенести/отменить. Агент скрывает CLI и ID, сообщает точные назначения, версию, дату/зону, состояние. Прямое разрешение точного действия не требует повторного вопроса. Неподдержанную команду агент не подтверждает как выполненную.

README, HANDOFF, AGENTS, API-NOTES и ADR отражают фактическую реализацию, experimental границу, обязательный live опыт, ограничения самоподтверждения, переноса/отмены и сверки. README самодостаточен: получение проекта, запуск и первый пост без знания исходного расположения у автора и этой переписки. Из ONBOARDING убрать локальный планировщик как альтернативу цели.

## 8. Проверки и приёмка — R23–R27

Старые 54 теста и JS syntax должны пройти. Новые тесты через public seams: даты/зоны и DST; fingerprint/stale version/settings/bot/rights; media payload с quote/Unicode/custom ID; proposal/approval timeout; crash между durable receipt и projection; восстановление без сети; повтор/конкурентный execute; блокировка непосредственной доставки; unsupported cancel/reschedule без сети; reconcile конфликтов; UI состояния и escaping. Реальный браузер desktop/mobile проверяет синтетические состояния, дату/зону, версии, фильтры и overflow.

Live R24–R27 нельзя доказать mock. Готовится воспроизводимый сценарий с выбранным человеком ботом/каналом/topic, скрытым token-set, конкретной версией (текст+quote+PNG/JPEG+MP4) и датой. Только валидный разрешённый custom ID. Человек разрешает live action. После durable approval прекращаются локальные исполнители; Telegram публикует; человек проверяет клиент; повторный запуск не создаёт пост. До этого результат: «экспериментальный адаптер подготовлен, серверная автономность не подтверждена».

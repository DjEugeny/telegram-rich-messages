# План развития

Решение пользователя от 18 октября 2026: текущий личный сервис завершается **без отложенных постов**. Основной поток: подготовить → посмотреть → поправить → разрешить непосредственную публикацию → проверить Telegram. Будущий функционал не задерживает эту версию.

## 1. Завершение текущего объёма

- Сохранить Rich Message, порядок медиа, версии, превью, историю и непосредственную отправку/правку с разрешением точного материала и назначения.
- Непосредственная публикация нового теста v1 в тестовый канал прошла после отдельного разрешения: API-успех и receipt сохранены, пользователь подтвердил выход/вложения; скриншот показывает автора-канал, текст/цитату/emoji и нужные медиа. visual_verified=true. Playback видео отдельно не подтверждён. Старый pending-эксперимент не повторялся и не заменяет этот результат.
- После этого отдельно согласовать открытый GitHub-репозиторий и проверить запуск из чистого ZIP/clone в новом чате. Новичок независимо выбирает существующий/новый канал и бота. Не нужны прежняя переписка, JSON, знание CLI, второй аккаунт или настройка direct messages.
- Native Windows/DPAPI и непосредственная доставка текущим ботом требуют собственной проверки; прежние синтетические тесты её не заменяют.

## 2. Отложенная публикация — отдельная будущая задача

Статус: отложено пользователем. Готового выбранного решения сейчас нет. Требования сохраняются: Rich Message со всеми блоками и медиа, публикация от имени своего канала, без второго аккаунта и без включённого компьютера/Codex в момент выхода. Новичок не администрирует хостинг.

Предпочтение — штатная передача Rich Message и даты на сторону Telegram, если официальный API даст проверяемый путь для канала и его бота. Сейчас такого пути в проекте не подтверждено: `sendRichMessage` не документирует прямое расписание в канале; Suggested Posts имеет отдельное согласование. Прежний опыт создал предложение, но не подтвердил расписание. [sendRichMessage](https://core.telegram.org/bots/api#sendrichmessage), [Suggested Posts](https://core.telegram.org/api/suggested-posts) (сверены 18 октября 2026).

Если штатного пути нет, **подходящее направление для новичков — управляемый сервис с подтверждённой поддержкой Rich Messages**. Срок и материал принимает сервер оператора сервиса, пользователь подключает бота/канал, не разворачивая сервер. Это архитектурная рекомендация, не выбранный поставщик и не реализованный функционал. Она меняет прежнее требование «исполняет Telegram» и потребует отдельного решения пользователя: где выполняется очередь, кто хранит токен/медиа, каковы стоимость и ответственность за пропуски/повторы. Деплой, оплата и передача секретов не разрешены этим планом.

| Кандидат | Текущий вывод |
| --- | --- |
| Suggested Posts → approve тем же админ-ботом | Эксперимент не дал расписания; не использовать в текущей версии. Сохранить receipts и разбирать без повтора записи |
| Controller Bot через пересылку Rich Message | Наш материал редактор пропустил, обычные сообщения принял. Пока не подходит этому сценарию; [протокол](controller-bot-check.md) |
| Управляемый сервер с `sendRichMessage` | Направление для отдельного выбора; нужны подтверждённая поддержка формата и оператор, снимающий хостинг с новичка |
| Локальный таймер/cron | Не выполняет условие выключенного компьютера; не добавлять скрыто |
| MTProto пользовательского аккаунта | Другая модель авторизации и доступа; не выбирать без отдельного решения. MTProto-запрос с токеном бота не решает проблему: документирован `SCHEDULE_BOT_NOT_ALLOWED` ([messages.sendMessage](https://core.telegram.org/method/messages.sendMessage)) |

До следующего опыта сначала проверить документацию и реальное сохранение rich-полей, затем получить разрешение конкретного материала/версии/канала/бота/даты. Приёмка будущей отложки: устойчивое принятие даты и материала → выключенный локальный исполнитель → фактический выход от имени канала → совпадение всех блоков/порядка/медиа → восстановление без дубля. Перенос, отмена, отказы и неизвестный результат проверяются отдельно. Отправка предложения, наступившие часы и mock-тесты не заменяют эту приёмку.

## 3. Сохранённый эксперимент

`scheduling.py`, таблицы и receipts оставлены для расследования/восстановления; CLI запрещает новые review/отправки до чтения токена и сети. Локальные list/recover/reconcile и возврат уже известного завершённого receipt сохраняются. Не обходить блокировку прямым вызовом Python API. В интерфейсе старые записи названы историей эксперимента; они не являются действующей очередью.

Технический долг прежнего опыта: сохранять безопасную причину определённого отказа API, отличать её от transport unknown, не терять диагностику при recover, корректно проецировать известный proposal ID из proposal receipt. Это задачи перед возвращением к адаптеру, не свидетельство готовности текущей отложки.

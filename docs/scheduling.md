# Расписание: карта реализации и пределы доказательств

Экспериментальный адаптер уже есть; частичный live-опыт 18 октября подтвердил создание pending-предложения, но не расписание. Одобрение тем же ботом не подтверждено, schedule receipt нет, recover восстановил `proposed`; пользователь сообщил об отсутствии поста в канале. Независимость от Mac не проверена. Текущая схема не пригодна как готовая автоматизация. Подробный [итог опыта](../HANDOFF.md) — в корне проекта; команды агента — `ONBOARDING.md`.

Следующий этап — исследование официального пути канал + его бот без второго аккаунта. Второй аккаунт был только тестовым и исключён пользователем из продуктового постинга/одобрения. Ручное принятие получателем не заменяет автоматизацию. [Официальное описание Suggested Posts](https://core.telegram.org/api/suggested-posts) описывает такое принятие для направления channel → user; не делать из этого вывод о неисправимости всего API. Код потерял причину ошибки одобрения, HTTP status не установлен. Новую архитектуру не выдумывать; локальный таймер, облачный cron и MTProto без отдельного решения не предлагать.

Онбординг должен работать по ссылке на будущий открытый репозиторий в новом чате, без прежней переписки. В начале агент предлагает независимо существующий или новый канал и существующего или нового бота; создание — только по выбранной человеком ветке, токен скрыто вводит человек. Для Ольги целевой канал — её существующий публичный, автор поста должен отображаться каналом. Сейчас проверяются отдельные тестовый канал и бот; отображение автора и пригодность рабочего назначения требуют проверки в Telegram. Публикация GitHub — последующий согласованный этап после live-проверки.

Перед ручным вводом токена агент определяет ОС, shell и cwd фактического запуска проекта. Человек получает одну подходящую инструкцию с собственной папкой: «Терминал»/`python3` на macOS или PowerShell/`py -3` на Windows, со скрытой вставкой токена и без изменения ExecutionPolicy. Remote/контейнер/WSL не приравниваются к компьютеру человека; ручной ввод и CLI должны использовать одну установку и среду. Неоднозначность уточняется. Linux/WSL не имеют поддержанного защищённого хранилища в текущем коде; plaintext fallback запрещён. Подробные шаги — в [ONBOARDING.md](../ONBOARDING.md).

## Поток данных

`Store` хранит неизменяемый материал. `Scheduling.configure` заменяет полный набор назначения/зоны в SQLite. `parse_schedule_time` возвращает абсолютный `iso`, UTC `send_date` и IANA `timezone`. `review` сохраняет snapshot конкретной версии/медиа, назначения, бота и даты, выдаёт operation ID/fingerprint. `execute` перепроверяет snapshot и под общей delivery.lock отправляет предложение, сохраняет proposal receipt, запрашивает одобрение даты и только при подтверждённом успехе сохраняет schedule receipt. Сетевой транспорт переиспользует `delivery.py`; токен получает только локальный процесс.

SQLite содержит `schedule_settings`, `schedule_operations`, `schedule_events`, `schedule_receipts`. Файловые JSON receipts пишутся атомарно с fsync до конечной проекции состояния; при невозможности записи файла остаётся SQLite receipt и требуется recover. `recover` без сети восстанавливает известное подтверждение или сохраняет блокирующий unknown. Повтор execute известного scheduled возвращает существующий receipt без повторной отправки. Взаимные guards запрещают одновременно активные расписание и непосредственную доставку одного поста.

## Состояния

| Состояние | Что известно |
|---|---|
| `reviewed` | Снимок проверен; человеческое разрешение ещё требуется |
| `sending` | Начато выполнение; повтор запрещён |
| `proposed` | Есть предложение; подтверждённого расписания нет |
| `approving` | Начато одобрение; результат ещё не сохранён |
| `scheduled` | Есть устойчивое подтверждение одобрения; выход ещё не доказан |
| `unknown` | Исход неоднозначен; recover/проверка человеком, без повтора |
| `error` | Зафиксирована ошибка либо доказанное отсутствие без receipts |
| `cancelled` | Ручной факт в допустимом переходе; не запрос отмены в Telegram |
| `published` | Человек подтвердил channel message ID и оставил evidence |

Известные proposal/schedule receipts запрещают `absent`. Известный `scheduled` со schedule receipt нельзя перевести в `cancelled` командой reconcile. `cancel/reschedule` возвращают unsupported без сети. Встроенного пути отказа от уже reviewed операции нет: не удалять записи вручную ради нового review, фиксировать блокер.

## Проекция для дашборда

`Scheduling.list()` возвращает `id`, `post_id`, `status`, `version`, `channel`, `channel_title`, `send_at`, `send_date`, `timezone`, `proposal_message_id`, `published_message_id`, `source`, `evidence`, `last_error`, `experimental`, `live_verified`. В HTML нет скрытого snapshot/fingerprint. `dashboard.build` читает согласованную версию через `Store.get(post_id, version)`, компилирует её HTML и прикрепляет безопасную проекцию к посту. Если версия недоступна, виден явный отказ, без подмены текущей версией.

UI разделяет согласованный материал и текущий черновик, показывает дату в зоне расписания и предупреждение после срока. Поиск охватывает заголовок и текст HTML, включая сохранённое содержимое; состояние выбирается отдельным фильтром. Пересечение даты не меняет статус на published. Дашборд остаётся статическим снимком после build; сетевой синхронизации и кнопок публикации нет.

## Ограничения

Требуются явные DM chat ID/topic канала и права администратора; обычная тема группы не подходит. Разбор времени требует базы IANA, поддерживает ISO и сегодня/завтра/послезавтра с точным временем, диапазон 300…2678400 секунд. DST-неоднозначность отклоняется. Native Windows и системные секретные хранилища не прошли реальную проверку. Mocks/HTTP-превью не подтверждают Telegram-клиент и независимость выхода от Mac. Локального таймера, cron, polling и MTProto-пути нет. Полная функция не принята: перенос/отмена не реализованы; узкий согласуемый опыт описан в [live-протоколе](scheduling-live-test.md).

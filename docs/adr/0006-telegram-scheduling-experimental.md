# ADR 0006. Экспериментальное расписание через Telegram suggested posts

## Контекст

Пост должен выходить на стороне Telegram после передачи согласованного материала и даты, когда Mac, Codex и локальный сервер выключены. Основание: `.autopilot/2026-10-18-telegram-scheduling--wip/spec.md` и `manifest.md`, включая D01. Пригодность API для Rich Message с медиа, самоодобрение ботом и автономный выход требуют live-проверки; локальные тесты её не заменяют.

## Решение

Использовать experimental-кандидат: `sendRichMessage` в direct messages канала с `suggested_post_parameters.send_date`, затем `approveSuggestedPost` с датой. Согласие связывается snapshot/fingerprint с версией, медиа, ботом, назначением, абсолютной датой и зоной. Локальный таймер, heartbeat Codex, облачный cron/сервис и классическое сообщение не являются заменой этого механизма.

До approve устойчиво сохранять proposal receipt; только строгое `True` одобрения и durable receipt дают `scheduled`. Receipts записывать атомарно с fsync до производных SQLite-проекций и HTML. Timeout или невалидный ответ дают блокирующий `unknown`: автоматический retry и новая отправка запрещены. Общая `delivery.lock` исключает конкурирующие операции; `recover` восстанавливает известные подтверждения без продолжения сети. Proposal ID не равен будущему channel message ID.

По D01 безопасная проекция `Scheduling.list()` содержит `post_id`, но не раскрывает скрытый snapshot. Дашборд получает согласованную версию через Store и показывает её отдельно от текущей; локальная правка не подменяет сохранённый материал.

## Почему

Suggested posts — кандидат на серверный выход без постоянно работающего исполнителя. Раздельные подтверждения proposal/approve и запрет повторов при неизвестном результате сокращают риск дублей и ложного статуса. D01 позволяет связать расписание с постом и показать прежнюю согласованную версию через публичный контракт.

## Последствия

Результат остаётся экспериментальным адаптером: live-приёмка API, медиа, вида в клиенте и выхода при остановленном исполнителе не доказана. Нужен отдельно разрешённый опыт с конкретной версией, ботом, назначением и датой; при отказе API фиксируется препятствие без заявления готовности.

`cancel/reschedule` возвращают `unsupported` без сети. Это честная граница поддержки, но не выполнение требований переноса и отмены. Прошедшее время не превращает `scheduled` в `published`; публикация требует проверенного человеком свидетельства с channel message ID. Список, rebuild и recovery Telegram не сверяют.

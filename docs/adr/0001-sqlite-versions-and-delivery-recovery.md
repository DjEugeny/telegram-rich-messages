# ADR 0001. SQLite, неизменяемые версии и восстановление доставки

## Контекст

Пост может редактироваться локально, отправляться в Telegram и затем исправляться в том же сообщении. Между запросом к Telegram, сохранением результата и пересборкой HTML возможны сбои. Потерянный ответ не доказывает, что сообщение не опубликовано. Требуется сохранять историю, связывать разрешение с конкретным состоянием и предотвращать случайную повторную отправку.

Основание: `spec.md`, S1 и S3; `manifest.md`, R17, R18, R25–R27.

## Решение

Использовать `data/state.sqlite3` для транзакционного состояния, неизменяемых версий и журнала операций. Исходники и экспорты версий хранить в `posts/`, материалы — в `media/`; локальные файлы заменять атомарно. Новая правка создаёт новую версию.

До сети сохранять operation UUID и snapshot: действие, хеш конкретной версии, назначение, бота и предыдущий `message_id`. Выполнение согласовывать через транзакционный захват `sending` и глобальную межпроцессную блокировку. Повтор той же операции не должен снова обращаться к сети. Обычная отправка уже опубликованного поста запрещена; сознательная новая публикация требует отдельного разрешения и `--new-publication`. Правка сохраняет `message_id`.

При возможном принятии запроса без достоверного результата фиксировать блокирующий `unknown`. После подтверждённого успеха сначала сохранять устойчивый receipt с `message_id`, затем обновлять локальное представление. Восстановление по receipt не выполняет сеть. Ручное разрешение неопределённости допускается только по проверенным фактам с указанием основания. Успех API и визуальная проверка в клиенте учитываются отдельно.

## Почему (альтернативы + почему отвергнуты)

Набор изменяемых JSON-файлов как единственный источник состояния не даёт общей транзакции для версии, операции и журнала. Перезапись текущего поста уничтожила бы состояние, на которое человек выдал разрешение. Поэтому выбраны SQLite и добавление версий вместо их изменения.

Автоматический повтор после timeout мог бы создать дубликат уже принятого сообщения. Проверка истории Telegram не выбрана как основание восстановления: спецификация не предусматривает её чтение. Ошибка пересборки HTML также не является основанием повторять успешный запрос. Receipt отделяет подтверждённый внешний результат от локального отображения.

## Последствия

Появляются явные состояния доставки, блокировки и процедуры восстановления. При `unknown` работа с отправкой останавливается до получения проверенного основания; это сознательная цена защиты от дубликатов. SQLite и файлы проекта нужно переносить согласованно при остановленных операциях, сохраняя receipts и неопределённые результаты. Решение снижает риск повторной отправки, но не обещает exactly-once.

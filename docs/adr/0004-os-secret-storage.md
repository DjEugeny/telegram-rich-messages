# ADR 0004. Системное хранение токена и скрытый ввод человеком

## Контекст

Для доставки нужен токен бота, однако агенту не требуется видеть его значение. Проект переносится между компьютерами; пользовательские данные, HTML, команды и диагностические сообщения не должны становиться каналами раскрытия секрета.

Основание: `spec.md`, S3 и S4; `manifest.md`, R21, R24 и R31.

## Решение

Хранить токен в macOS Keychain с передачей через stdin системному `security` CLI либо в Windows DPAPI-файле с ACL текущего пользователя. Команду `token-set` запускает человек в своём терминале со скрытым вводом через `getpass`. Fallback с отображением ввода запрещён; агент не читает хранилище.

Не включать токен в аргументы процессов, логи, HTML и данные постов. Исключения и описания API редактировать или обобщать перед выводом, не выводить URL с токеном. Приватные файлы исключать из Git. После переноса проекта на другой компьютер человек вводит токен заново.

## Почему (альтернативы + почему отвергнуты)

Открытый текст в настройках проекта упростил бы копирование, но связал бы перенос материалов с переносом секрета. Передача через аргументы команды создала бы дополнительную поверхность раскрытия. Ввод через чат сделал бы значение доступным агенту и истории разговора. Эти варианты отвергнуты в пользу системной защиты и отдельного локального ввода человеком.

Fallback с echo мог бы позволить продолжить настройку в неподходящем терминале, но нарушил бы обязательную скрытость ввода. Поэтому отсутствие безопасного ввода должно останавливать настройку, а не ослаблять её условия.

## Последствия

Работа с секретами зависит от механизмов конкретной ОС и требует отдельной настройки на каждом компьютере. Перенос материалов не переносит готовую авторизацию бота. Проверки с подменённым хранилищем не подтверждают работу настоящих Keychain/DPAPI: manifest отдельно отмечает, что реальные хранилища и native Windows не запускались. Этот ADR фиксирует выбранный способ, а не результат такой проверки.

# Протокол согласованной live-проверки расписания

Статус: **прежний протокол; частичный опыт остановился до подтверждённого расписания**. 18 октября 2026 создано pending-предложение с медиа, одобрение тем же ботом не подтверждено; schedule receipt нет, recover восстановил `proposed`. Пользователь сообщил об отсутствии поста в канале. Вызовы не повторялись. Это не завершённая проверка автономности от Mac; подробный [итог опыта](../HANDOFF.md) — в начале HANDOFF. Причина API-ошибки потеряна кодом, конкретный HTTP status и неисправимость всего подхода не установлены.

Следующий этап — исследовать официальный путь канал + его бот без второго аккаунта. Второй аккаунт был исключительно тестовым; пользователь исключил его из продуктового постинга и одобрения. [Официальное описание Suggested Posts](https://core.telegram.org/api/suggested-posts) описывает подтверждение пользователем-получателем для направления channel → user; ручное одобрение не заменяет автоматизацию. Текущая схема не готова; перенос/отмена не реализованы. Прежние шаги ниже сохранены для истории, **не разрешают повторить вызовы или привлечь второй аккаунт**. Не предлагать новую архитектуру, локальный таймер, облачный cron или MTProto без отдельного решения.

## Карточка опыта: заполнить по этапам

До `schedule-review` заполнить назначение, материал/версию/медиа, дату/зону, ожидаемого бота, свидетеля и план остановки Mac. Получить отдельное согласие на сетевой preflight. Данные, которые возвращает review, заполняются после него; разрешение execute — только после показа результата.

| Поле | Значение для согласования |
|---|---|
| Отдельный тестовый канал | Название и подтверждённый числовой channel ID |
| Direct messages канала | Проверенный числовой DM chat ID; соответствующий parent channel |
| Тема direct messages | Проверенный topic ID; не тема обычной группы |
| Ожидаемый бот, до review | Известное человеку имя/username выбранного бота |
| Материал | Post ID, версия, fingerprint версии, текст и превью |
| Медиа | Порядок, типы, группы, SHA256; реальные доступные image/video |
| Custom emoji | Либо отсутствует, либо разрешённый валидный ID с fallback |
| Дата выхода | Абсолютная ISO-дата/время, IANA-зона и UTC timestamp |
| Разрешение preflight, до review | Формулировка согласия на сетевую проверку и время получения |
| Проверенный бот, после review | Возвращённые username/bot ID и права публикации/direct messages |
| Operation, после review | Operation ID и confirmation fingerprint из результата review |
| Свидетель | Кто проверяет клиент Telegram с другого устройства |
| Остановка Mac | Кто останавливает исполнители и фиксирует время выключения |
| Разрешение execute, после review | Отдельное согласие на показанные версию, бота, назначение и дату; время получения |

Не подставлять демонстрационные ID. До заполнения полей «до review» и согласия на preflight сеть не вызывать. После review дополнить карточку проверенным ботом и operation ID/fingerprint; до отдельного согласия на execute предложение не отправлять. Токен человек вводит скрыто через `python3 tool.py token-set` в своём терминале; агент его не читает и не получает в чат. Windows: `py -3` вместо `python3`, но native Windows ещё не проверен.

## Последовательность

1. Человек включает прямые сообщения тестового канала, добавляет бота и выдаёт права `can_post_messages`/`can_manage_direct_messages`. Подтверждает числовые channel/DM/topic IDs. Не читать updates общего бота и не менять webhook ради поиска ID.
2. Агент создаёт вымышленный пост с согласованными текстом, цитатой, image/video и группировкой. Сохраняет конкретную версию и хеши; выполняет `build`, показывает превью и состав медиа. Не использовать вымышленный demo custom ID для live-теста.
3. Выбрать дату с запасом на проверку и остановку Mac. Явно выбрать IANA-зону; `Asia/Novosibirsk` — текущая зона владельца, но не молчаливый выбор для канала. Выполнить локальные настройки и проверку времени. Значения заглавными буквами ниже — поля карточки, не готовые аргументы:

```sh
python3 tool.py schedule-config --channel CHANNEL_ID --dm-chat-id DM_CHAT_ID --topic-id TOPIC_ID --timezone IANA_ZONE
python3 tool.py schedule-time "ABSOLUTE_ISO_DATETIME" --timezone IANA_ZONE
```

Локальный диапазон — 300…2678400 секунд; реальный API может отказать. Настройки заменяются целиком, поэтому передать всё назначение. Неоднозначное время/DST или недоступная база IANA — остановка с уточнением, без угадывания.

4. Получить разрешение именно сетевой проверки этого назначения. `schedule-review` не публикует предложение, но вызывает preflight. Затем выполнить:

```sh
python3 tool.py schedule-review POST_ID "ABSOLUTE_ISO_DATETIME" --experimental
```

Сверить возвращённого бота, DM-чат и parent channel с карточкой. Права конкретного topic подтверждает только отправка. Показать человеку актуальные текст/медиа, post ID, версию/хеш, бота, channel/DM/topic, абсолютную дату и зону, operation ID и экспериментальное ограничение. При ошибке API/прав/назначения — сохранить безопасный диагноз и остановиться.

5. Получить разрешение конкретной версии и операции. Пример формулировки после подстановки фактов: «Разрешаю экспериментальную постановку поста [ID], версии [N], ботом [ID] в тестовый канал [ID], DM [ID], topic [ID], на [абсолютная дата, время, зона]». Предыдущее поручение реализовать функцию и наличие `--experimental` этого согласия не заменяют. При изменении любого поля остановиться: нужен актуальный review и разрешение; существующую запись вручную не удалять.
6. После согласия выполнить:

```sh
python3 tool.py schedule-execute OPERATION_ID --fingerprint CONFIRMATION_FINGERPRINT --experimental
python3 tool.py schedule-list
python3 tool.py build
```

Сохранить устойчивые proposal/schedule receipts и безопасный результат без токена/credential URL. Записать ID предложения DM отдельно от будущего channel message ID. «Запланирован» допустимо только при подтверждённом `scheduled`. `proposed`, `approving`, `unknown` не доказывают расписание.

При обрыве не повторять execute и не создавать замену: сначала `schedule-recover` без сети, затем проверить receipts. Известный успех восстанавливать; при неизвестном исходе опыт заблокирован до проверенных фактов. Отказ/неясный ответ — результат опыта, а не повод переходить на обычный sendPhoto, локальный таймер или другой бот.

7. Человек проверяет в Telegram предложение и указанное время. До срока выхода остановить локальные серверы/исполнители, закрыть Codex и выключить Mac. Записать точное время остановки/выключения. С этого момента до выхода не запускать локальные команды. Не добавлять cron/облачный процесс/heartbeat для выполнения публикации.
8. После срока свидетель на другом устройстве проверяет канал. Записать фактическое время появления, channel message ID, текст/цитату, медиа и их порядок/группы, воспроизведение видео, custom emoji при наличии. Отсутствие поста или неполное оформление зафиксировать как неуспех/частичный результат. Один API-ответ и факт наступления времени эту проверку не заменяют.
9. После включения Mac выполнить `schedule-recover`, `schedule-list`, `build` без новой постановки. Убедиться в сохранности версии и receipts, отсутствии дубликата. Только при известном schedule receipt и проверенном человеком опубликованном сообщении:

```sh
python3 tool.py schedule-reconcile OPERATION_ID --verdict published --message-id VERIFIED_CHANNEL_MESSAGE_ID --evidence "Конкретный свидетель проверил канал, время, версию и медиа после выключения Mac"
python3 tool.py build
```

Подставить реальное свидетельство. `published` — ручной факт; `live_verified` кодом остаётся false. Не использовать `absent` при известном proposal/schedule receipt. `reconcile` не отменяет Telegram-пост; известный `scheduled` со schedule receipt нельзя пометить cancelled.

## Решение по результату

В `HANDOFF.md` записать заполненную карточку без секретов, безопасные ответы API/ID, статусы/receipts, время выключения и фактического выхода, свидетельство клиента, восстановление после запуска и отсутствие повтора.

Успех узкого опыта: Rich Message/медиа приняты и сохранены, устойчивое расписание получено, Mac выключен до срока, клиент с другого устройства подтвердил правильный пост в нужное время, повторное открытие не создало дубликат. Иначе — конкретный доказанный блокер или частичный результат; автономность не объявлять готовой.

Перенос/отмена **не реализованы**, поэтому полная исходная функция остаётся непринятой даже при успехе этого опыта. Их реализация/проверка и другой путь при непригодности Suggested Posts требуют отдельного решения и разрешения внешних действий. GitHub-публикация в этот протокол не входит.
